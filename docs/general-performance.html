Evaluation contract

General Performance Benchmark v2

Across pinned public repositories, how much retrieval context and tool work does a skygrep-first agent policy use relative to an rg-only policy, after both meet the same task-quality floor?

The older 4.05× result remains a deterministic six-task CI receipt. It is not a general multiplier. General Benchmark v2 separates correctness, context efficiency, and measured retrieval latency so none can hide a regression in another dimension.

Every task has a canonical path, optional accepted alternatives, at least two literal evidence terms, at least two quality terms, and a public ground-truth note. Validation fails if a commit, origin, tracked worktree, accepted path, or evidence term drifts. Each report also records the benchmark source commit and whether its tracked worktree was clean.

Quality before efficiency

  • Both policies must complete the paired task and achieve quality ≥ 0.85.
  • skygrep must remain within two percentage points of rg for aggregate quality and completion.
  • A general claim needs at least 30 unique eligible tasks across three repositories and at least 80% eligible paired observations.
  • Repeated trials stabilize measurement but do not increase the unique-task count.
  • The benchmark source must be one full Git commit with a clean tracked worktree; all six parallel receipts must use that same commit.

The quality score is a deterministic, auditable retrieval-context proxy based on accepted paths, literal source facts, noise control, sufficiency, and stopping behavior. It does not claim that an unobserved downstream model wrote a correct final answer.

Only after these gates pass does the report calculate context-token and tool-call reduction, measured harness-wall and retrieval-tool elapsed ratios, cross-task and per-repository distributions after taking each task's median across trials, ratio-of-sums, and a 95% hierarchical-bootstrap interval over repositories and unique tasks. Harness wall time includes deterministic scoring and token counting; retrieval tool time is captured before token counting.

Run cadence

Full General Benchmark v2Before a performance release or on explicit requestAccelerator required; six full public indexes plus paired trials

The scheduled GitHub workflow validates the protocol on a standard hosted runner; it does not mint a new performance receipt. The full workflow is a manual dispatch targeting a self-hosted runner labeled skygrep-benchmark. It first fresh-indexes Cobra and projects the other five workloads from exact chunk and capped-model-input counts, stopping before the large indexes if any projection exceeds the index timeout. Local reruns reuse completed indexes unless the index format, embedding model, or pinned source changes.

Reproduce

python -m pip install -e ".[benchmark]"
python benchmarks/validate_public_fixtures.py \
  --oss-root /tmp/skygrep-general-v2-repos --prepare
python benchmarks/universal_closed_loop_benchmark.py \
  --oss-root /tmp/skygrep-general-v2-repos --prepare \
  --refresh-index --reset-index --index-timeout 18000 --trials 3 \
  --tokenizer tiktoken --report /tmp/skygrep-general-v2.json \
  --summary-only
python benchmarks/closed_loop_regression_gate.py \
  /tmp/skygrep-general-v2.json --require-general-reportable

The first run builds six complete semantic indexes and can take hours on a CPU-only or memory-constrained machine. Index elapsed is recorded separately and never enters the retrieval-efficiency headline. Omit --refresh-index --reset-index on later query-only repetitions.

The manual accelerated workflow runs the six repositories after the capacity gate, then merges compact rows and recomputes one aggregate quality gate and confidence interval. Capacity, per-repository, and merged receipts are retained as artifacts. The weekly protocol workflow validates pins and benchmark logic without presenting protocol validation as a fresh performance result.

Claim boundary

This is a retrieval-workflow benchmark. Its quality gate scores retrieved source support rather than a model-generated final answer. Token counts cover tool context, not hidden model reasoning, final-answer output, cache billing, or provider pricing. A provider end-to-end claim additionally requires the same model, prompt, temperature, agent loop, and provider usage receipts in both conditions.
